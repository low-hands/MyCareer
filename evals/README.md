# 分层评估流程

先用便宜的检查定位问题，方向确定后才扩大真实模型采样。实验阶段不全量重录。

| 层次 | 什么时候跑 | 范围与成本 |
|---|---|---|
| 确定性测试 | 每次相关代码、配置、提示或 schema 改动 | 脚本化假模型，验证路由、授权、交付、汇总和评估器；不调模型 |
| 重放已有录制 | 每次相关改动 | 离线验证现有轨迹与 runtime；不调模型或 embedding |
| 定向真实录制 | 实验阶段 | 只选可能受影响的几个场景，各固定采样 10–30 次 |
| 两套全量重录 | 准备合并时一次 | 最终版本固定后，Qwen、DeepSeek 的 47 条轨迹及现有 runtime 护栏统一录制 |

## 每次改动

先跑相关确定性检查，再重放已有录制。提示/schema 未变是复用录制的重要前提，还须通过场景、上下文快照及语义录制的有效性检查。前提不符时明确报告 stale/missing，不修改 hash，不把过期结果算作质量通过；实验阶段也不因此自动启动全量录制。

确定性测试验证代码和护栏，重放验证当前代码如何处理已经录下的模型行为，两者都不能证明新提示的模型质量。

## 实验阶段

修改前先列出受影响行为，例如工具后继续解释、多步查询汇总、跨轮续接、岗位分析/匹配链路。只选对应场景，在采样前固定输入、判分、模型及每场景次数，通常 10–30 次。按场景报告成功数/分母、失败类型及不确定性；同时保留 pass^k，但不只靠三次全过比例判断方向。

生产提示使用抽象原则或独立例子，不复制评估/holdout 原话。提示改动有全量重录成本，应集中设计后一次验证。下一份 holdout 在采样前明确：并列查询按工具集合核对，只有用户指定或执行依赖要求的先后关系才按顺序判定。冻结 holdout 不跟随结果调整，失败和基础设施异常全部保留；判分误判另写审计，不覆盖原始成绩。新结果使用独立实验目录，不覆盖历史基线。

## 准备合并

确认实现与提示/schema 不再调整后，统一重录两套全量，并检查有效性、行为与质量护栏。全量重录是最终验证，不是每次小改的默认动作。若之后又改了提示/schema 或其他关键评估前提，需要重新判断哪些最终结果失效；不要把旧结果标成最终版。

连接故障、缺失或过期录制须单列，不能宣称全量验证完成；也不要反复重录失败场景直到刷绿。

具体命令与指标见 [Runtime 质量评估](runtime_quality/README.md)。延迟采用 [分阶段基线](latency/README.md)，不拿短合成场景的耗时推断自然使用性能。
